## Goal

The first real RAG loop: embed the V2 chunks, store them in a vector store, retrieve the top-k provisions for a question, and generate a grounded answer with source references. The architecture becomes API-less "service → retrieval → vector store → LLM" per [[Home]]. Equally important: prove — against the [[V1 - Minimal LLM Application]] baseline — that retrieval actually fixes the hallucinations you recorded.

**You'll have learned:** embeddings and vector similarity, pgvector/vector-store mechanics, docker-compose for local infra, grounded prompt construction, and the debugging discipline of testing retrieval separately from generation.

## Decisions

- **2026-08-22:** Local infra (vector store / Postgres) runs via `docker-compose`, introduced here rather than in V0, since this is the first version that actually needs a running service (see [[V0 - Project Foundation]] Decisions).
- **2026-08-22:** Vector store: **pgvector inside Postgres**, not a dedicated vector database (Qdrant/Weaviate/Chroma/…). One database serves vectors now *and* the structured/lexical needs of [[V5 - Hybrid Retrieval]] and [[V6 - Legal Structure and Citations]] — one service to run, one query language, and hybrid search stays in-database. A dedicated store is justified at scales/feature-needs this project won't reach; revisit only if pgvector measurably falls short.
- **2026-11-16 (step 1): image `pgvector/pgvector:0.8.7-pg18` via `compose.yaml` (option A), pinned, named volume, port bound to 127.0.0.1.** Rejected: building pgvector on the official `postgres` image (B — re-does published work) and a Homebrew install (C — not reproducible). Details and the PG18 volume-path gotcha in [[Docker Compose]].
- **2026-11-16 (step 1): `CREATE EXTENSION IF NOT EXISTS vector` belongs to step 2's schema SQL, not a compose init script** — the learner's choice (option 2). Init scripts run only on a fresh volume and are silently skipped afterwards; the schema SQL runs on every load and is idempotent. Compose stays pure infrastructure.
- **2026-11-16 (step 1): `database_url` is a `PostgresDsn`, not `str`** — a malformed URL fails when `Settings` loads, not at the first query. The default carries a committed local-only password; a hosted database later gets its URL from `.env` and is the moment to consider `SecretStr`.
- **2026-11-16 (step 2): one `chunks` table — a row is a chunk; the whole `Chunk` as `jsonb`, filter columns promoted, the embedding beside it (option A).** Rejected: normalised `acts`/`articles`/`chunks` (B — structure nobody queries before [[V6 - Legal Structure and Citations]]) and one wide column-per-field table (C — hand-written row↔`Chunk` mapping becomes a second definition of `Chunk`). Reading a row back is `Chunk.model_validate(row["chunk"])`; Pydantic stays the only definition of the shape.
  - **Columns:** `key text PRIMARY KEY` (step 4 upserts on it) · `chunk jsonb NOT NULL` (source of truth) · promoted, **generated from `chunk` by Postgres** (`GENERATED ALWAYS AS (…) STORED`): `document_id`, `act_type`, `act_number`, `act_year int`, `instrument_article` (null outside a ratified instrument), `article`, `paragraph` · `embedding vector(n) NOT NULL` · `embedding_model text NOT NULL` (mixing two models' vectors becomes detectable) · `embedded_text_hash text NOT NULL` (sha256 of `embedding_text`; step 4 skips unchanged chunks).
  - **Generated columns are the tutor's refinement of A, made 2026-11-16:** A's one weakness was the promoted columns drifting from the JSON. If Postgres computes them from `chunk`, they cannot — the same "derive, never store twice" rule `SourceReference.citation` follows. Cost: the expressions are JSON paths that must follow the model's field names; a renamed field fails at insert, loudly.
  - **The dimension `n` waits for step 3** — learner's choice over swapping steps or an unsized `vector` (which cannot be indexed).
- **2026-11-16 (step 2): plain `schema.sql` applied by `psycopg`, every statement `IF NOT EXISTS`, starting with `CREATE EXTENSION IF NOT EXISTS vector`.** No ORM, no migration tool until the schema first *changes* (expected V5/V6). See Tools & Alternatives.
- **2026-11-17 (step 2): generated columns are `NOT NULL` wherever the model's field is required** (`document_id`, `act_type`, `act_number`, `act_year`, `article`); `paragraph` and `instrument_article` stay nullable. Without it a renamed Pydantic field would fill the column with NULLs and filters would quietly match nothing; with it the first insert fails. `->>` (text, SQL NULL for JSON null), never `->`, for the last step of each path — a test pins it.
- **2026-11-17 (step 2): database tests run against the compose Postgres under a `db` marker, each inside a transaction that is rolled back.** Rejected for now: a separate test database or testcontainers — more machinery than one table needs. Cost: `poe test-all` needs `poe up`. `apply_schema` does not commit; the caller owns the transaction (`main()` commits by leaving the `with psycopg.connect(...)` block cleanly).
- **2026-11-17 (step 4): stale rows are pruned (option A), scoped to the documents this run read.** `DELETE … WHERE document_id = ANY(loaded documents) AND key <> ALL(loaded keys)`. The document list comes from the chunks read, never from the manifest or the file names, so a missing or empty `.jsonl` can never wipe an act; an empty `.jsonl` stops the load outright. Rejected: upsert only (B — a deleted provision stays retrievable and citable) and truncate-and-reload (C — re-embeds everything every run).
- **2026-11-17 (step 4): an `Embedder` protocol, batch-shaped — `embed(texts: list[str]) -> list[list[float]]` plus `model`** (option A over one text per call). `OllamaEmbedder` owns step 3's rules (`truncate: false`, `num_ctx` 8 192) and refuses a response unless it has one vector of `EMBEDDING_DIMENSIONS` per text. Own error types (`EmbeddingUnavailableError`, `…RequestError`, `…ProtocolError`), without V1's transient/permanent split — nothing retries. Model and context are constants in `compositions.py`, not settings: changing the model is a schema change and a re-embed.
- **2026-11-17 (step 4): vectors cross to Postgres through the `pgvector` package** (`register_vector(conn)`, `Vector(...)`), not hand-formatted text literals.
- **2026-11-17 (step 4): commit per batch, prune last (option B)** — the tutor revised the earlier "one transaction" proposal. A crash keeps the finished batches and the hash skip resumes from there; the DELETE runs only after every batch succeeded, so a failed run never prunes. Cost: mid-run, a reader may see some chunks updated and others not yet; each row is self-consistent.
- **2026-11-17 (step 4): three outcomes per chunk, not two — embed, rewrite metadata, or skip.** The tutor's addition: `path` is not in `embedding_text`, so a container-title fix (e.g. V2's «ΑΤΟΜΙΚΟ ΕΡΓ ΑΤΙΚΟ» kerning debt) leaves the hash unchanged; skipping on the hash alone would keep the stale JSON forever. A row is skipped only if hash, model *and* JSON all match.
- **2026-11-17 (step 4): `load` tests isolate by a throwaway Postgres schema per test** (`CREATE SCHEMA test_load_…`, `search_path`, `DROP … CASCADE`), because `load` commits and a rollback cannot undo it. Step 2's tests keep the rollback approach.

- **2026-11-18 (step 5): a `Retriever` protocol + `PgVectorRetriever(conn, embedder)` (option B).** Same shape as `LLMClient` / `Embedder`: step 7's service receives a `Retriever` and its tests pass a fake; V5's hybrid retriever is a second implementation. Rejected: a plain `search(conn, embedder, question, k)` function (A — the seam would be extracted one step later anyway) and a SQL function in Postgres (C — logic outside mypy and the test suite, and V5's fusion happens in Python).
- **2026-11-18 (step 5): exact search, cosine `<=>`, no index.** Measured at the kickoff: `EXPLAIN ANALYZE` shows a sequential scan + top-N heapsort over 2 136 rows in **12 ms**. bge-m3's stored vectors all have norm 1.0000 ± 1e-6, so `<=>`, `<#>` and `<->` rank identically; `<=>` was chosen because it stays right for a model that does not normalise and matches `vector_cosine_ops` for a future HNSW index. `ORDER BY` repeats the expression (not the alias) — the form pgvector's index planner recognises.
- **2026-11-18 (step 5): `WHERE embedding_model = embedder.model`.** A question embedded by one model, compared against another's vectors, returns plausible garbage without an error. The column exists since step 2 for exactly this.
- **2026-11-18 (step 5): the caller owns the connection; default `k = 5`.** Connection: same rule as `apply_schema` and `load`; a pool is V8's problem (FastAPI). k: step 3's Recall@5 was 17/17 for bge-m3.
- **2026-11-18 (step 5): an empty result raises `NoEmbeddingsError` ("run `poe load`"), never returns `[]`.** With exact search, zero rows can only mean no vectors for the model — a setup failure. Returned as `[]`, step 7 would turn it into a confident "not found" for every question.
- **2026-11-18 (step 5): no distance cut-off.** "Nothing relevant" needs a threshold calibrated on real distances, and none exist yet. Step 6 reads them; the "not found" path stays with the step 7 prompt until the numbers say otherwise.
- **2026-11-23 (step 6): a re-runnable runner, not ad-hoc `poe search` (option B).** One Markdown sheet to read + one JSON record per run, so [[V5 - Hybrid Retrieval]] has a "before". Rejected: hand-run searches with notes (A — not repeatable) and labelled Recall/MRR (C — V4's job, and it skips the reading). `expected` is *shown* beside the hits, never scored.
- **2026-11-23 (step 6): the p01–p04 questions are colloquial on purpose,** written without opening the law, so retrieval is not flattered by the legislator's own wording. Answerability was checked by keyword search over `data/processed/` and reading the articles — not by the vector search being judged.
- **2026-11-23 (step 6): no distance threshold — confirmed.** Out-of-corpus x1/x2 score 0.462/0.463 at rank 1; answerable p04/p02/q04/q10 score 0.408–0.432. The bands overlap; "not found" belongs to the step 7 prompt.
- **2026-11-23 (step 6): keep `DEFAULT_K = 5`.** k = 10 would rescue only q04 (rank 8); q03 (24) and p04 (60) are beyond any reasonable k, and every extra chunk is prompt tokens.
- **2026-11-23 (step 7): prompt layout B — rules in the system message; the retrieved provisions, each labelled with its full citation (`chunk.source.citation`) and article title, then the question, in the user message.** The model cites only those labels; when they don't cover the question it writes one fixed "not found" sentence (countable by string match in steps 9–10). Rejected: provisions in the system prompt (A — mixes versioned rules with per-call data) and JSON structured output with cited keys (C — changes the `LLMClient` seam, tends to degrade an 8B model's Greek, and moves two variables at once; structured citations are [[V6 - Legal Structure and Citations]]'s). The V1 prompt and no-retrieval path stay frozen beside the new one. Learner agreed.
- **2026-11-23 (step 7): the LLM's context window is ours — `num_ctx` = 8 192, sent by `OllamaClient` on every chat.** Measured: krikri's Modelfile sets `num_ctx 131072`, and `ollama ps` showed it loaded at **31 GB** (~6 GB weights, ~25 GB cache and buffers). Prompts need at most ~7 500 tokens (top-5 context max 10 500 chars ≈ 2 700 tokens at krikri's ~3.9 chars/token, +4 000 if the 15 679-char chunk is retrieved, + rules, question, answer). The earlier worry — silent truncation by a small default — does not apply to krikri; the reason is memory, and that a Modelfile is the publisher's config: switching models would change the window with no diff here. Constant `LLM_NUM_CTX` in `compositions.py`, beside `EMBEDDING_NUM_CTX`. **Verified 2026-11-23:** after `ollama stop` and one `poe ask`, `ollama ps` shows CONTEXT 8192, SIZE **7.1 GB** (was 31 GB). `poe lint` clean, `poe test` 301 passed (299 + 2 new).
- **2026-11-23 (step 7): the grounded prompt is a second prompt beside V1's, not a rewrite of it.** `GROUNDED_SYSTEM_PROMPT` / `GROUNDED_PROMPT_VERSION = "v2"` / `NOT_FOUND_ANSWER` / `build_grounded_messages(question, chunks: list[Chunk])` in `application/prompts.py`; `SYSTEM_PROMPT` "v1" and `build_messages` frozen, so `poe baseline` stays reproducible and "v2 rules, no retrieval" remains possible as a tiebreaker. Seven rules: answer only from the provisions (1); cite by **copying the «Διάταξη:» label** = `chunk.source.citation` (2 — checkable in step 8); watch which act a provision belongs to (3 — the q10 guard); fixed not-found sentence, with a partial-answer path (4); never claim a law does not exist (5 — **V1 bug b**); identifying provisions *is* the task, no lawyer redirect (6 — **V1 bug a**); Greek (7). Dropped from v1: the amendments rule (the model reads, it no longer recalls) and the closing disclaimer (it conflicts with "write only this sentence", and may have prompted the role dodge — the disclaimer becomes application text, step 8). Not in the prompt: distances (uncalibrated, step 6) and few-shot examples (only if step 9 shows the rules ignored). The user message: «Διατάξεις:», each provision as `Διάταξη:` / optional `Τίτλος άρθρου:` / `Κείμενο:` (`chunk.text`, never `embedding_text`), separated by `---`, nearest first, then `Ερώτηση:` last. 9 tests in `tests/test_prompts.py` (incl. a v2 fingerprint); `poe test` 310 passed.
- **2026-11-23 (step 7): krikri stays the model for steps 7–9** (learner's choice). qwen 30b, installed, would make step 9's V1-vs-V3 comparison move model and retrieval at once; it is a separate experiment afterwards. Side finding, undecided: krikri's Modelfile also sets `temperature 0.5`, which our client does not override — answers are not reproducible run to run.

Changing `embedding_text` now would make step 9's V1-vs-V3 comparison measure two retrieval versions at once — V1's "one variable at a time" requirement.
